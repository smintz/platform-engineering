# Coding Conventions

**Analysis Date:** 2026-09-07

This is a Protoconf repository: Starlark (`.pinc`/`.mpconf`) constructs Protocol Buffer
messages defined in `.proto` files, and `protoconf compile` materializes them as JSON
(`materialized_config/`) plus side-channel Terraform/YAML (`outputs/`). There is no
application code — everything below is Starlark and proto convention.

## Repository Layout Convention

| Path | Role |
|------|------|
| `src/platform/` | The platform core — component model, hook plumbing, monitoring. Driver-agnostic. |
| `src/platform/v1/platform.proto` | The one hand-written schema: `Component`, `Objective`, `FailureDomain`, `State`. |
| `src/terraform/`, `test/src/terraform/` | Generated by protoconf-terraform. **Never hand-edit.** |
| `drivers/<kind>/<name>/src/` | One Protoconf module per driver, each its own `remote_repo`. |
| `test/` | The only entry point — `test/src/core_test.mpconf` plus its own `CONFIGSPACE`/`Makefile`. |
| `materialized_config/`, `outputs/` | Compiler-written. Never hand-edit. |

**Drivers are separate modules, not packages.** `test/CONFIGSPACE` declares one
`remote_repo` per driver (`github_actions`, `grafana`, `ecs`, `kubernetes`,
`terraform_state`) so importing Grafana does not drag in ECS. A second monitoring or CI
driver is a new directory under `drivers/<kind>/`, never a branch inside an existing one.
Each driver carries a `src/v1/dummy.proto` (`drivers/state/terraform/src/v1/dummy.proto`)
purely so the module has a descriptor set.

## Naming Patterns

**Files:**
- `.pinc` libraries named after what they expose: `core.pinc`, `monitoring.pinc`,
  `grafana.pinc`, `kubernetes.pinc`.
- Driver entry library is `<driver_name>.pinc` at the driver's `src/` root; sub-libraries
  go in a subdirectory (`drivers/monitoring/grafana/src/grafana/alerts.pinc`).
- `.proto` files live under a versioned directory: `src/platform/v1/platform.proto`,
  `drivers/monitoring/grafana/src/grafana/v1/dashboard.proto`.
- Entry points are `.mpconf` and live in `test/src/` (`test/src/core_test.mpconf`).

**Starlark symbols:**
- `WithX(...)` — a hook factory. Public API of every library
  (`WithSLO`, `WithConfig`, `WithFailureDomain`, `WithContainerEnv`, `WithState`,
  `WithGrafanaDashboard`, `WithMonitoring`, `WithDiagnostic`).
- `PascalCase` — public factories and constructors that are not hooks
  (`Component`, `Workload`, `S3Backend`, `KubeConfig`, `TerraformPipeline`, `GetConfigs`).
- `snake_case` — plumbing and predicates (`chain`, `flatten`, `message_filter`,
  `component_filter`, `terraform_filter`, `mutate_config`).
- `_leading_underscore` — module-private helpers (`_backend`, `_slug`, `_plan_id`,
  `_apply_id`, `_backend_state_id`, `_unsafe` in
  `drivers/cicd/github_actions/src/github_actions.pinc`).
- `UPPER_SNAKE` — module constants (`MAIN_CONFIG`, `MONITORING_CONFIG`,
  `TERRAFORM_VERSION`, `LOCK_TIMEOUT`, `KUBECONFIG`, `GRAFANA_UNITS`, `SLO_W`).
- Inner hook function is always named `do` or `hook`; the chain continuation is always
  `next`.

**Proto:** `snake_case` fields, `PascalCase` messages, nested messages for sub-structures
(`Component.Objective.Query`), enums prefixed with the type name and a
`*_UNSPECIFIED = 0` zero value (`STATUS_UNSPECIFIED`, `TYPE_UNSPECIFIED`,
`UNIT_UNSPECIFIED`) — see `src/platform/v1/platform.proto`.

## Code Style

**Formatter:** `black` (via `make fmt` → `protoconf fmt -w`). `.vscode/settings.json`
associates `.pconf`/`.mpconf`/`.pinc`/`.proto-validator` with the Starlark language,
`.materialized_JSON` with JSON, sets `ms-python.black-formatter` as the Starlark
formatter, and enables `editor.formatOnSave`.

**Linting:** none configured. Correctness is enforced by the compiler and by proto typing.

**Comment style — this is the strongest convention in the repo.** Every public symbol
carries a prose block comment above it explaining *why the design is this shape*, not what
the code does. Comments name the alternative that was rejected and the failure it would
cause. Examples worth imitating:
- `drivers/runtime/kubernetes/src/kubernetes.pinc` — why Kubernetes and ECS are not
  behind one "runtime" interface, and why `config_context` is only set when non-empty
  (proto2 presence semantics).
- `drivers/state/terraform/src/terraform.pinc:14-22` — why `settings` and `config_for`
  are written from one description.
- `src/platform/core.pinc` — why `inherited` hooks run first, why the main config is
  mutated before the component chain.

Match this register when adding code: a new hook without a rationale comment is out of
place here.

**`ponytail:` comments** mark deliberate shortcuts with a named ceiling and an upgrade
path. Two live ones: `src/platform/core.pinc` (configs default to Terraform on re-open;
deferred hooks see only the downstream component). Use the same prefix for new shortcuts.

## Import Organization

`load()` order is alphabetical by path, with cross-module `@label//` loads first, then
`//`-rooted local loads, then Starlark stdlib. See `test/src/core_test.mpconf` and
`drivers/monitoring/grafana/src/grafana.pinc`.

```python
load("@platform//platform/platform.pinc", "platform")   # another module
load("//platform/v1/platform.proto", component_proto = "Component")  # this module
load("encoding/json.star", "json")                       # stdlib
load("re.star", "re")
load("any.star", "any")
```

**Aliasing convention:** proto message types imported into Starlark that would shadow a
Starlark symbol get an explicit alias — `component_proto = "Component"`,
`TerraformProto = "Terraform"`, `tf = "util"`. Local shorthands for deep nested types are
assigned at module level rather than repeated: `Pod = KubernetesDeployment.Spec.Template.Spec`,
`Settings = TerraformProto.TerraformSettings`, `Unit = component_proto.Objective.Query.Unit`.

**Facade export:** `src/platform/platform.pinc` re-exports the whole platform surface as a
single `struct` so a call site needs one `load` line instead of a dozen. It loads
`core.pinc` and `monitoring.pinc` and they never load it back — the dependency is
one-directional by design.

## The Hook Pattern (the core idiom)

Everything composable is a hook: `(msg, next) -> msg`, produced by a `With*` factory.

```python
def WithDescription(description):
    def do(component, next):
        component.description = description
        return next(component)

    return component_filter(do)
```

`chain(msg, *hooks)` in `src/platform/core.pinc` runs them in order.

**Typed hooks.** One call site configures several message types at once. Every hook
declares its target type by wrapping in `message_filter(prototype, *hooks)`; non-matching
messages pass straight through. Two named wrappers exist — use them rather than raw
`message_filter`:
- `component_filter(*hooks)` — fires on `platform.v1.Component`.
- `terraform_filter(*hooks)` — fires on `terraform.v1.Terraform`.

A hook that mutates a Terraform config (e.g. `WithContainerEnv` in
`drivers/runtime/kubernetes/src/kubernetes.pinc`) is left unwrapped and is applied by
`WithConfig`/`mutate_config` against the config message.

**Markers, not hooks.** Things that are not "mutate this message" are passed in the same
variadic list as `module(...)` values and partitioned by `type(h) == "module"` inside
`Component` (`src/platform/core.pinc`). Four kinds:

| Marker | `kind` | Meaning |
|--------|--------|---------|
| `WithDeps(*factories)` | `deps` | Upstream components, passed *uninstantiated*; `Component` builds each with the inherited hooks. |
| `ForDownstream(*hooks)` | `downstream` | Hooks parked on this component, run against whoever depends on it. |
| `Finally(*hooks)` | `finalize` | Hooks that must see the finished component (rendering a view of what was declared). |
| `Inherit(*hooks)` | `inherit` | Hooks that also apply to every transitive dependency. |

When adding a new capability, ask whether it mutates the message *now*. If not, it is a
marker — forcing it into `(msg, next)` makes it fire at the wrong time.

**Macros returning several hooks** return a tuple; `flatten(hooks)` in `Component` splices
them so the call site stays one line.

**Config storage.** A component holds `map<string, google.protobuf.Any> configs`. Keys are
paths that become files (`MAIN_CONFIG = "infra/main.tf.json"`,
`MONITORING_CONFIG = "monitoring/main.tf.json"`). `mutate_config(component, key, *hooks)`
is the single primitive every config write goes through; `WithConfig(key, *hooks)` is its
declarative wrapper (a `None` key means the main config). Unpacking requires a prototype,
so `CONFIG_TYPES` maps `type_url -> prototype`; configs not in that registry are treated as
driver scratch space and are never rendered.

**Bare messages as hooks.** `mutate_config` accepts a non-function positional and wraps it
in `tf.From(...)` — "replace the config with this one". Preserve that when writing a
similar entry point.

## Output Mapping

`main()` in `test/src/core_test.mpconf` returns a dict; each key with a `.json`/`.yaml`
extension before `.materialized_JSON` is also written verbatim under
`test/outputs/core_test/`. `GetConfigs()` keys configs as
`"<domain>/<name>/<config key>"` — the domain/name prefix is applied only there, once the
whole chain has run and the values are final.

## Error Handling

`fail("...")` at compile time is the only mechanism, and messages are prefixed with the
function that raised them and explain the fix, not just the fault:

```python
fail("TerraformPipeline: no Terraform configs to build a pipeline from")
fail("%s and %s produce the same job id %s" % (owner[id], key, id))
fail(
    "LocalBackend: reading one local state from another needs an explicit " +
    "path_for — the default state file is relative to whichever directory " +
    "terraform ran in, which the reading state cannot resolve",
)
```

Sites: `drivers/state/terraform/src/terraform.pinc:56`,
`drivers/cicd/github_actions/src/github_actions.pinc:124,169,585,603`,
`drivers/monitoring/grafana/src/grafana.pinc:359`,
`drivers/monitoring/grafana/src/grafana/alerts.pinc:83,262`.

**Prefer returning `None` over failing when an unknown input costs an edge rather than
produces a wrong one** — `_backend_state_id` returns `None` for backends it cannot name,
and a `None` never matches (`drivers/cicd/github_actions/src/github_actions.pinc`).

## Validation Idioms

**No `buf.validate.field` / `validate.rules` annotations and no `.proto-validator` files
exist in this repo today.** Validation is currently structural: proto typing rejects
unknown fields and wrong types at compile, and `fail()` covers the cross-field rules.

When adding validation, follow the Protoconf split:
- **Single-field** (range, regex, enum membership, non-empty) → annotate the field in the
  `.proto` with `(buf.validate.field).<rule>`. The natural first candidates are
  `Objective.Query.min`/`max` (ratio bounds) and `Component.name`.
- **Cross-field** (`min <= max`, "an alerted objective must set `burn_query` or
  `threshold_alert`", referential integrity between `configs` keys) → a
  `.proto-validator` Starlark file next to `src/platform/v1/platform.proto` registering
  `add_validator(Component, fn)`.

Prefer either over a `fail()` inside a driver: a validator blocks the materialized file
from being written at all, which is a stronger guarantee than one driver noticing.

## Function Design

- Closures over configuration, not classes. `_backend(kind, settings, config_for, key_for)`
  returns a `struct(state=, remote=, key_for=)`; `S3Backend`/`LocalBackend` are thin
  descriptions fed into it.
- Public factories take positional required args, then keyword args with defaults, then
  `*hooks` **last** (`WithSLO`, `Component`, `Workload`).
- Explicit `if provider == None` rather than truthiness where an all-default proto message
  is a meaningful value — an empty `Kubernetes()` is falsy but means "in-cluster creds"
  (`drivers/runtime/kubernetes/src/kubernetes.pinc`).
- Zero-value awareness: proto3 omits defaults from output, so `min`/`max` reading back as
  `0` is documented at the definition site rather than guarded everywhere.

## Module Design

- A `.pinc` exposes either loose symbols (`core.pinc`, `terraform.pinc`, `kubernetes.pinc`)
  or a single `struct` namespace (`platform` in `platform.pinc`, `actions` in
  `github_actions.pinc`, `lib` in `github/lib.pinc`, `alerts` in `grafana/alerts.pinc`).
  Use the struct when the surface is wide enough that a call site would otherwise collect
  a load line per hook.
- Module-level dicts/lists are frozen after `load()`. Merge into a fresh local rather than
  updating a constant in place.
- Call-site policy (bucket names, datasource names, key layouts) never lives in a driver.
  `test/src/core_test.mpconf` owns `BACKEND`, `DATASOURCES`, `OUTPUT_ROOT`, `WINDOW` and
  the PromQL; drivers know only kinds and shapes.
