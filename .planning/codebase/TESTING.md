# Testing Patterns

**Analysis Date:** 2026-09-07

## Test Framework

**There is no unit test framework.** No pytest, no Go test, no Starlark assertion harness.
Correctness is established by three layers, in this order:

1. **The compiler.** `protoconf compile` type-checks every Starlark-to-proto assignment.
   An unknown field, a wrong type, or a failed `fail()` blocks the materialized file from
   being written.
2. **Golden output.** `test/materialized_config/` and `test/outputs/` are committed. A
   change that should be behaviour-preserving is proved by recompiling and getting an
   empty `git diff` on those trees; a change that should alter output is reviewed as the
   diff.
3. **`terraform validate` and `terraform plan` in CI**, run against the generated
   `main.tf.json` files — this is what catches a config that compiles but is not valid
   Terraform.
4. **Negative checks (`make gates`, phase 01-04).** Layers 1-3 only ever compile inputs
   that are correct, so a deleted `fail()` guard is invisible to all three. `make gates`
   feeds each of the two CI-driver compile gates the wiring it exists to reject, compiling
   a mutated COPY of `test/src/handshake_test.mpconf`, and asserts on the gate's own
   message plus the gate function named in the traceback — never on the exit code, since
   both mutations exit non-zero for reasons unrelated to the gate. It runs from `make test`,
   so `drift.yaml` covers it.

## The `test/` Module

`test/` is a self-contained Protoconf workspace that exercises the platform and every
driver end to end. It is the repo's only entry point — nothing else in the repository
materializes anything.

| File | Role |
|------|------|
| `test/src/core_test.mpconf` | The scenario. Declares `RedisComponent` and `ApiTaskComponent`, wires the dependency, and returns the output map from `main()`. |
| `test/CONFIGSPACE` | Declares the module under test (`platform=remote_repo(url="..")`) and each driver as its own `remote_repo`. |
| `test/protoconf.lock` | Pinned `fileDescriptorSetSum` per dependency. Regenerated by `protoconf mod tidy`. |
| `test/Makefile` | The runner. |
| `test/.protoconf_cache/*.fds` | Fetched descriptor sets — gitignored (`.protoconf_cache` in `.gitignore`). |
| `test/src/terraform/**` | Generated provider/resource schemas (protoconf-terraform). Not hand-edited. |
| `test/materialized_config/core_test/**` | Golden materialized JSON. |
| `test/outputs/core_test/**` | Golden side-channel output: four `main.tf.json` files plus the workflow YAML. |

**What the scenario covers.** `test/src/core_test.mpconf` is deliberately built to exercise
every mechanism at once:
- Two components with a real dependency (`platform.WithDeps(RedisComponent)`).
- `ForDownstream` — Redis injects `REDIS_URL` into the API's containers.
- `Inherit` — `WithFailureDomain("us-east-1")` propagates from `api-task` to `redis`.
- Two configs per component (`infra/main.tf.json` and `monitoring/main.tf.json`), proving
  the split-state design.
- `WithSLO`, `WithDiagnostic`, burn queries, units, severities.
- Cross-state reads (S3 backend + `terraform_remote_state`), which is what the CI driver
  recovers job ordering from.

Four output states result: `us-east-1/{api-task,redis}/{infra,monitoring}`. Adding a
mechanism to the platform means extending this scenario so it shows up in the golden diff.

## Run Commands

```bash
make                     # root: fmt + protoconf compile -process-templates .
make fmt                 # protoconf fmt -w   (black-equivalent formatting)
make build               # protoconf compile -process-templates .
make clean               # rm -rf outputs materialized_config .github/workflows/*

cd test && make test     # the real test: mod tidy + compile + install workflows + gates
cd test && make workflows # copy outputs/core_test/.github/workflows/*.yaml to repo root
cd test && make gates    # the negative tests: prove both compile gates still fire
```

`test/Makefile`:
```make
test:
	protoconf mod tidy
	protoconf compile .
	$(MAKE) workflows
	$(MAKE) gates
```

`workflows` exists because GitHub only reads `.github/workflows` at the repository root,
so the compiler-written workflow under `test/outputs/` is copied there.
**`.github/workflows/terraform.yaml` is generated — edit `test/src/core_test.mpconf`, not
the YAML.**

## Verification Loop

```bash
cd test && make test
git diff --stat materialized_config outputs ../.github/workflows
```

- Empty diff on a refactor → behaviour preserved.
- Non-empty diff → read it; it is the test result.
- Compile fails → the Starlark traceback points at the file and line.

For a faster loop on one entry point: `protoconf compile . core_test.mpconf` from `test/`
(strip the `src/` prefix — a wrong path exits 0 and silently writes nothing).

**Debugging:** `print(...)` anywhere in `.pinc`/`.mpconf` writes to stderr at compile time.
Remove before committing.

## Mocking

None, and none is needed — compilation touches no network or cloud API. The nearest
equivalents are the substitution seams the drivers already provide:

- **Backends** are injected, not hardcoded. `S3Backend(...)` in `core_test.mpconf` can be
  swapped for `LocalBackend(path_for)` from `drivers/state/terraform/src/terraform.pinc`
  to produce a stack that applies against local state with no AWS at all.
- **Datasource names** come from the call site (`DATASOURCES = {"prometheus": "Prometheus"}`).
- **Runtime driver** is a load line: swapping `@kubernetes//kubernetes.pinc` for
  `@ecs//ecs.pinc` changes what a component deploys onto without touching the platform.

## Coverage

No coverage tooling. The practical coverage measure is whether a mechanism appears in
`test/outputs/core_test/`. Uncovered today:

- `drivers/runtime/ecs/src/ecs.pinc` — the ECS runtime driver is not exercised by
  `core_test.mpconf`, which uses Kubernetes. Its output has no golden file.
- `LocalBackend`, `gcs`, `azurerm` and `remote` backends in
  `drivers/state/terraform/src/terraform.pinc` — only `S3Backend` is exercised, though
  `_backend_state_id` in the CI driver handles all five.
- `Finally` and `Check`-style objectives (`Component.Objective.Check` is a TODO stub in
  `src/platform/v1/platform.proto`).
- Negative tests exist for exactly two `fail()` paths — `_check_remote_backends` and
  `_check_reads_are_produced`, covered by `make gates` (phase 01-04). Every other `fail()`
  in the platform and the drivers is still unasserted: nothing proves the job-id collision
  check, the cycle check, or any validator actually fires.

## CI

**One workflow: `.github/workflows/terraform.yaml`** — and it is generated by
`actions.TerraformPipeline(...)` in `test/src/core_test.mpconf` via
`drivers/cicd/github_actions/src/github_actions.pinc`.

**Triggers:**
```yaml
pull_request: { paths: [test/outputs/core_test/**] }
push:         { branches: [main], paths: [test/outputs/core_test/**] }
schedule:     [{ cron: "0 3 * * *" }]
workflow_dispatch: {}
```

**This pipeline still does not run `protoconf compile`** — it plans and applies the
*committed* generated Terraform. That gap is now covered by a second, separate workflow.

**`.github/workflows/drift.yaml`** (hand-written, phase 01-01, FOUND-01) is the compile check:
it triggers on `test/src/**`, `src/**`, `drivers/**`, `test/CONFIGSPACE`, `test/protoconf.lock`
and `.github/workflows/terraform.yaml` — source paths, so it fires on the exact failure the
generated pipeline's `test/outputs/**` filter cannot see. It installs a sha256-pinned
`protoconf v0.2.0-rc2`, deletes the machine-local `test/protoconf.lock` (its committed
`file:///Users/...` paths break `mod tidy` on any runner), runs `cd test && make test`, then
`git add -A --` and `git diff --cached --exit-code --` over `test/materialized_config/`,
`test/outputs/` and `.github/workflows/terraform.yaml`. Staging before diffing is what makes a
*new* output directory fail rather than pass green. `test/protoconf.lock` is deliberately
outside the assertion: CI regenerates it every run.

A contributor who edits `.mpconf` without running `cd test && make test` now gets a red
`drift` check naming the fix.

**Jobs (per state, four states):**

| Job | What it runs |
|-----|--------------|
| `plan_<slug>` | checkout → AWS OIDC (`vars.TF_PLAN_ROLE`) → [Grafana token] → `setup-terraform@v3` (1.9.8) → plugin cache → `terraform init -lock-timeout=5m` → `terraform validate -no-color` → `terraform plan -detailed-exitcode -out=tfplan` → upload `tfplan` + `plan.txt` (5 day retention). |
| `apply_<slug>` | `needs: plan_<slug>`; gated on `push` to `main` **and** `plan.outputs.changes == 'true'` → OIDC (`vars.TF_APPLY_ROLE`) → download plan artifact → `terraform apply -auto-approve tfplan`. |
| `pr_comment` | `needs` every plan job; downloads all plan artifacts and upserts a single sticky PR comment (tagged `<!-- tf-plan -->`) with a per-state result table and truncated plan bodies. |

**Notable mechanics, all generated from the config graph rather than hand-written:**

- **Job ordering is derived, not declared.** The driver matches a config's backend
  bucket/key against another config's `terraform_remote_state` bucket/key
  (`_backend_state_id` / `_state_id`) to recover the apply order. Nothing in a component
  restates its own pipeline.
- **Job ids** come from the config key: `_slug` collapses everything outside
  `[a-zA-Z0-9]` to `_`, prefixed `plan_`/`apply_`. Collisions `fail()` at compile
  (`github_actions.pinc:603`).
- **Detailed exit code handling** — `terraform plan -detailed-exitcode`, exit `0` →
  `changes=false`, `2` → `changes=true`, anything else re-raised.
- **Drift detection** — on `schedule`, a plan that reports changes fails the job with
  `::error::drift detected in <label>`.
- **Grafana credentials are minted per job**, only on the monitoring states whose config
  declares the Grafana provider: an AWS Managed Grafana service account token with
  `--seconds-to-live 1800`, masked with `::add-mask::`, exported through `$GITHUB_ENV`,
  with expired tokens on the account reaped first.
- **Permissions** are least-privilege: `contents: read`, `id-token: write` (OIDC),
  `pull-requests: write`. No long-lived cloud credentials anywhere.
- **Concurrency group** `terraform-${{ github.ref }}`.
- **PR comment budget** — capped at 60000 chars, share split evenly across changed
  states so one large plan cannot crowd out the others.

## Adding Coverage

1. Extend `test/src/core_test.mpconf` so the new mechanism appears in a component.
2. `cd test && make test`.
3. Review the diff in `test/materialized_config/`, `test/outputs/` and
   `.github/workflows/terraform.yaml` — that diff is the assertion.
4. Commit the golden files with the change.

For a new driver: add it to `test/CONFIGSPACE` as its own `remote_repo`, `protoconf mod
tidy` to refresh `test/protoconf.lock`, then wire it into a component in the scenario.

For a validator (`.proto-validator` or `buf.validate.field`): deliberately break a config
and confirm the compile fails and the materialized file is *not* written, then fix it. A
validator that never trips is worse than none.
